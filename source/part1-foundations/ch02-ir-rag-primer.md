
## 为什么

“检索增强生成”（Retrieval-Augmented Generation）通常被浓缩成两句话：*把文档切块、给每块算 embedding、取用户查询的 top-k 最近邻、拼进 prompt。* 这种说法不能说错，只能说它是能给出的最短说法，而且恰好掉进了“汽车就是四个轮子加一台发动机”那种认知陷阱 —— 技术上挑不出毛病，但在排查问题时一点用都没有。

这句定义背后藏着一条工程师只能用教训换来的道理：*知识库最难的不是“写出来”，而是“找得到、用得上、跟得上”* {cite}`fanyamin2026kb_pipeline`。本章的每一节，归根结底都是在拆解这一句。“找得到”对应检索；“用得上”对应融合与评估；“跟得上”对应索引过期之后各种下游的故障模式。

信息检索（IR）作为一个学科，大约已经有六十年的历史 {cite}`manning2008introduction`，积累下一整套术语、一整套评估方法，以及一份很长的失败模式清单 —— 设计者要是没先读过这份清单，每一个落地的知识库都会把这些坑重新踩一遍。本章先给出全书后文会默认你掌握的最小 IR / RAG 词汇表，再做三件大多数 RAG 短文会跳过的事：诚实地列出 vanilla RAG 的失败模式、把 GraphRAG 作为其中一类失败的严肃替代方案介绍给你、最后用一张判断矩阵告诉你怎么选检索底座 —— 全文搜索、pgvector、Elasticsearch，还是专用向量数据库 {cite}`fanyamin2026elasticsearch_rag` {cite}`fanyamin2026pgvector_rag`。对 BM25、稠密检索、混合检索、GraphRAG 文献以及底座取舍已经熟悉的读者，可以直接翻过去，只留意记号即可。

## 是什么

六个术语撑起了全书后文几乎所有的重量；在这里精确地定义一次，后面的章节就能少写很多铺垫。再加两个术语 —— RAG 的失败模式清单以及 GraphRAG —— 就撑起了你在文献里会看到的大部分争论。

### 词法检索：TF-IDF 与 BM25

词法检索为文档对查询打分，依据三件事：*哪些查询词出现*、*出现了几次*（term frequency，词频）、以及*它们在整个语料里有多罕见*（inverse document frequency，逆文档频率）。TF-IDF 是最早的公式 {cite}`manning2008introduction`；BM25 则是那个被一线打磨出来的改进版 —— 现代所有主流全文搜索引擎 （Lucene、Elasticsearch、Tantivy、PostgreSQL 的 `tsvector`、Bleve）归根结底都是 BM25 的衍生 {cite}`robertson2009probabilistic`。在代码知识库这个场景里，基于标识符的 BM25 强得意外：标识符本身就带着很强的信号，一个分词分得好的 BM25 索引，在 *“找出 `runSync` 的所有调用点”* 这类精确符号查询上，常常能轻松打赢一个调得不好的 embedding 模型。

花一页讲讲 *为什么* BM25 管用是值得的，因为大多数工程师是通过一次库函数调用见到 BM25 的，根本看不到它的答案形状。对于一个由词项 $t_1, t_2, \dots$ 组成的查询 $q$，以及一篇长度为 $|D|$、所在索引的平均文档长度为 $\text{avgdl}$ 的文档 $D$，BM25 给二者打的分是对查询词项的一个求和：

$$
\text{BM25}(q, D) \;=\; \sum_{t \in q}
  \underbrace{\text{IDF}(t)}_{\text{how rare is }t?}
  \;\cdot\;
  \underbrace{\frac{f(t, D)\,(k_1 + 1)}
                   {f(t, D) + k_1\!\left(1 - b + b\,\frac{|D|}{\text{avgdl}}\right)}}_{\text{saturating, length-normalised TF}}.
$$

从左到右读一遍，三个设计决策就从公式里浮现出来：

1.  **罕见词主导。** IDF 因子使得：语料中只在 1% 的文档里出现过的词项，其贡献远大于在一半文档里出现过的词项。这正是构建良好的 BM25 索引能精准命中标识符查询的原因：像 `ERR_QUEUE_DRAIN` 这样的错误码只出现在寥寥几份文档里，IDF 值极高，包含它的文档会以大幅领先胜出。这也解释了为什么在"搜这个精确符号"的场景下，BM25 往往能跑赢向量检索：*向量不知道"罕见"是什么意思*。

2.  **词频是饱和的。** 不同于原始 TF-IDF —— 一个词项重复出现十次就把贡献乘以十 —— BM25 的 TF 分子上界被限制在 $(k_1 + 1)$。在 Elasticsearch 默认的 $k_1 = 1.2$ 下，一个词项的第十次出现几乎不比第三次多贡献任何东西。这个性质恰恰就是 BM25 不会被 `keyword keyword keyword keyword` 式的堆砌欺骗、而 TF-IDF 会的原因。对代码知识库的启示是：*当一个标识符在生成的文件里确实合法地出现了两百次时，TF 饱和正是你想要的行为*。

3.  **长度是归一化的，但只归一半。** $b$ 参数（默认 $0.75$）控制 BM25 对长文档施加惩罚的力度。$b=0$ 时长度无关紧要；$b=1$ 时长度是平均值两倍的文档，其等效词频会被减半。中间地带是刻意的选择：长文档确实有更多"碰巧"提到某个词项的机会，但它们也确实覆盖了更多内容。对一个文档长度从 50 词的 ADR 存根跨到 5000 词 runbook 的软件知识库而言，$b$ 的选择比 $k_1$ 的选择更关键。

实践里，$k_1 \in [1.2, 2.0]$ 和 $b \in [0.5, 0.9]$ 几乎能覆盖所有生产场景。常见的错误是先调这两个，再调分词器 —— 顺序是反的。下面四个众所周知的 BM25 病症值得记在本子上，因为它们每一个迟早都会在真实知识库里冒出来：

-   **短查询敏感性。** 在单词查询上，BM25 退化为"哪份文档对该词有最高的 IDF 加权 TF"，如果那个词恰好是一个常见动词，结果就不可靠了。补救办法：查询扩展，或让稠密检索器并行跑、最后再做融合。
-   **词汇不匹配。** *"wait for the pool to finish"* 和 *"drainOnShutdown"* 没有任何共同的查询词项，因此 BM25 给出的得分是零。这不是 BM25 的 bug，而正是稠密检索作为互补而存在的理由。
-   **复合词断裂。** `drainOnShutdown` 若被索引为一个 token，那么人类查询 *"drain on shutdown"* 就永远看不到它。三行分词器配置 —— 驼峰拆分、下划线拆分、可选的语言模型子词兜底 —— 通常比三周的 embedding 模型微调更管用。第 10 章会详细展开这个问题。
-   **停用词不对称。** 朴素的停用词移除会把 *not*、*or*、*no*、*nil* 从查询中剥掉，而在软件知识库里，这意味着 *"does it return nil"* 和 *"does it return"* 变成了同一条查询。第三部分的代码层检索器保留了这些词。

还有另一类查询，BM25 不是兜底，而是主力：*字面标识符*（identifier-literal）查询。用户搜订单号 `20260115`、HTTP 状态码 `502` 或工单 `PROJECT-1234` 时，要的不是 *“一些感觉上跟 502 有关的段落”*，要的是 *“那段明确提到了 `20260115` 的话”*。向量检索遇到 `20260115`，会一本正经地给你返回一段关于“如何创建订单”的介绍 —— 因为它在语义空间里看起来就是挨着的；而 BM25 会直接返回真正包含这个字面量的那一段 {cite}`fanyamin2026elasticsearch_rag`。任何一个用户会问字面标识符问题的知识库 —— 对软件类知识库来说几乎就是全部 —— 就必须保留一条 BM25 通路，没有商量。

### 稠密检索：embedding 与 ANN

稠密检索把稀疏的词袋表示换成神经编码器生成的稠密向量，然后在这个向量空间里找邻居。它的现代祖师爷是 Dense Passage Retrieval（DPR）{cite}`karpukhin2020dpr`；让它能工业化的规模化技巧，是为近似最近邻搜索（ANN）设计的 HNSW （Hierarchical Navigable Small World）图 {cite}`malkov2020hnsw` —— pgvector 以及大多数生产级向量库底下用的都是它。稠密检索的强项在于“意译”：*“哪个函数在等 worker pool 排空？”* 这种查询一个词都不用和目标重合，它依然能把 `drainOnShutdown` 找出来。

需要时刻提醒自己的反面是：稠密检索的效果，顶多只能到它编码器训练分布的水平。一个几乎没见过 Go 代码的通用编码器，会把 `ctx.Done()` 和 `context.Background()` 放得比应有的更近；一个真正在代码上训练过的编码器 —— 比如 Voyage 的 `voyage-code` 或 BGE 家族 {cite}`voyage_code2` {cite}`xiao2024bge` —— 才会把它们分开。选编码器要按你的领域选，别盯着 MTEB 通用榜。

### 混合检索与 Reciprocal Rank Fusion

词法检索和稠密检索的失败模式是互补的 —— 这正是融合（fusion）能帮上忙的典型场景。生产环境里大多数混合系统用的都是 Reciprocal Rank Fusion（RRF）{cite}`cormack2009rrf`，一方面因为它是“无分数（score-free）”的，两边的排序器都不必做分数校准，另一方面因为它几乎没什么可调的旋钮。对代码知识库而言，第三部分（第 10 – 12 章）会反复论证：*混合不是可选项* —— 纯词法漏意译，纯稠密漏精确符号，而融合比你二选一要便宜得多。

有两根本应属于混合层的操纵杆 —— 也是纯向量库流水线通常会丢掉的 —— 值得在这里点名，因为它们对检索性格的改变，比你换任何 embedding 模型都大：

-   **字段加权。** 出现在文档 *标题* 里的 token，比相同 token 埋在正文里，对"这篇文档在讲什么"的指示信号要强得多。生产级的 Elasticsearch / Solr / pgvector + `tsvector` 配置通常把标题字段的权重设为正文字段的大约两倍；这对 nDCG@10 的提升幅度，超过了上游的大部分选择 {cite}`fanyamin2026elasticsearch_rag`。
-   **函数评分（新鲜度、权威度、热度）。** 一份在词法 + 稠密相似度上得分很高、但三年没更新过的文档，对大多数知识库问题而言，是一个比"相似度只有九成、但上周刚更新"的文档更差的答案。把融合得分乘上一个新鲜度衰减函数，就能把这种直觉变成一个正式的排序因子，而不是事后补丁 {cite}`fanyamin2026elasticsearch_rag`。

结构化过滤 —— *“只要 `worker` 包下的页面”、“只要打了 `runbook` 标签的文档”、“只要当前大版本”* —— 是第三根操纵杆，放到第 10 章单独讨论。在这里只强调一个现实问题：一旦结构化过滤进入视野，检索底座的选择（pgvector？Elasticsearch？专用向量数据库？）就不再是口味问题。本章“怎么做”一节会给出一张判断矩阵 {cite}`fanyamin2026pgvector_rag`。

### 重排：第二阶段的检索器

融合给你一条更好的 *列表* ；重排（Re-ranking）给你一个更好的 *top-k* 。这个区别值得仔细厘清：“加一个 reranker”这条建议被说得太多、被解释得太少，以至于很多团队把它实现成“调一下 Cohere Rerank”，然后就再也没搞清楚那个模型到底替他们干了什么。

架子是两段式的。第一阶段是融合过的 BM25 + 稠密检索，速度快、覆盖整个索引，被要求返回一个 *慷慨的* top-k —— 典型值是 50 或 100 个候选。第二阶段就是那个 reranker，速度慢、只对这些候选动手，被要求把它们重新排成最终送进 LLM 的 top-k（通常是 5 到 10）。第一阶段优化的是 *召回率* （“对的文档上没上 top-100？”），第二阶段优化的是 *小 k 下的精度* （“对的文档是不是就在第 1 位？”）。哪一阶段都做不好另一阶段的事，这也正是两段式成为主流生产范式的原因 {cite}`nogueira2019passage`。

第二阶段之所以必须单独存在，技术原因可以归结到一个架构抉择：**双编码器**（bi-encoder）与 **交叉编码器**（cross-encoder）之争 {cite}`reimers2019sbert`。

-   **双编码器**（bi-encoder）—— 本章到此为止提到的每一个稠密检索器都是这种架构 —— 分别把查询和文档编码成两个*独立的*向量，然后用一个廉价的相似度函数（余弦、点积）打分。文档的编码成本在索引期一次性支付；查询期只需编码查询，然后在几百万个预计算的向量上做 ANN 搜索。十亿级文档也是可行的。代价在表征力：模型只能比较两个固定向量，永远看不到查询和文档之间*具体 token 级别的交互*。
-   **交叉编码器**（cross-encoder）把查询和文档拼成一个输入 —— 形如 `[CLS] query [SEP] document [SEP]` —— 然后把整段拼接送入 transformer，输出一个相关性得分。因为 attention 在两侧之间跨越运行，模型可以直接衡量*查询中的哪个 token 和文档中的哪个 token 对齐*，而这恰恰是区分"泛泛地讨论限流"和"讨论 ingest 端点上的限流"所需要的信号。代价是计算量：每一对 (查询, 文档) 都是一次独立的 transformer 前向传播，因此你负担不起对整个索引跑交叉编码器。但对 100 个候选跑，是负担得起的。

这就是重排必须单独成一阶段的全部理由。双编码器在语料规模上给你召回，交叉编码器在候选名单上给你精度。想让其中一个去干另一个的活，不是赔质量，就是赔钱。

给点数量级的感觉：一个现代的交叉编码器 reranker 在 CPU 上大约能每秒打分 50 – 200 对 (查询, 文档)，单张消费级 GPU 能到每秒 500 – 2000 对。第一阶段给 top-100、每个查询预算 100ms 以内，这个数量级是舒舒服服能吃下的；第一阶段给 top-1000、预算还是那个，就吃不下了。实用结论是： *第一阶段的 top-k 是一个成本旋钮* ，不是一个精度旋钮 —— 越过某个点之后，再加召回只是在买延迟，而对最终答案没有帮助。

三类开权重 reranker 值得认识一下，因为它们几乎覆盖了整个设计空间，且都不会把你锁死在某家厂商上：

-   **MS MARCO 交叉编码器** —— sentence-transformers 家族，在微软 880 万篇段落的 MS MARCO 数据集上训练 {cite}`nogueira2019passage`。稳健、被充分理解、基准测试覆盖面广。英文知识库的理想默认选择。
-   **BGE reranker** —— 与前面已经提到的 BGE embedding 模型同属一族 {cite}`xiao2024bge`；支持多语言，小型变体（约 3 亿参数）可以单卡部署。适合知识库是多语言混合的场景，或者你希望 embedding 和 reranking 统一供应商时使用。
-   **托管 API**（Cohere Rerank、Voyage Rerank、Jina Rerank）。质量/成本比通常没问题，集成成本几乎为零，运维关切也很直截了当：*每一条查询现在都要跟一个外部服务说话了*。如果你的知识库刻意不把私有代码发到外部，这就是一票否决；如果是公开文档类知识库，则往往是第一刀最合适的选择。

采用之前，四条诚实的提醒：

1.  **Reranker 能让一个"凑合"的检索器看起来不错，但救不了一个"坏掉"的检索器。** 如果第一阶段召回率就不行 —— 对的文档根本没进 top-100 —— 交叉编码器也没法检索出一份它从来没见过的文档。那些报告说"我们加了 reranking 之后质量反而*下降了*"的团队，几乎无一例外是在加完 reranker 之后调了第一阶段，让它返回更少、更"自信"的候选，结果是把第二阶段饿死了。
2.  **延迟是累加的，不是隐藏的。** 30ms 的混合检索之上再加一个 50ms 的交叉编码器，是 80ms 才到 LLM 的第一个 token，不是 30ms。对于每个回合要做多次检索的 agent 循环，这个数字累积起来很快。第 21 章关于 agent 的讨论会回到这个预算。
3.  **有了 reranker 之后，评估变得更重要而不是更不重要。** Reranker 可以用一种在三条样例查询上看起来正确、但在长尾上全错的方式重排一个列表。第 15 章的 BEIR 风格评估仍然留在原地，它移到了 reranker 的下游，而不是绕开它。
4.  **Reranker 不能替代其他操纵杆。** 在融合阶段施加的字段加权和新鲜度衰减仍然重要；交叉编码器完全不知道它给了高分的那份文档已经三年没更新了。健康的心智模型是：*融合负责组装一份带有正确结构偏置的候选列表；reranker 在这些偏置之内做重排*。

对本书面向的那些负载，诚实的建议是：在混合检索 + 字段加权 + 新鲜度衰减已经量化过，并且明显还把精度留在桌上之前，不要急着加 reranker。真要加的时候，用第一阶段同一套 BEIR 风格的评估脚手架去量，把第一阶段的 top-k 封在你真的负担得起的范围内，并把 reranker 藏在一个接口后面保持可替换 —— 以便你把 MS MARCO 换成 BGE、再换成某个托管 API 时，不需要重写整个检索层。第 12 章里代码层的参考实现正是这样接入交叉编码器的。

### 检索增强生成（RAG）

Retrieval-Augmented Generation（RAG）由 Lewis 等人正式定型 {cite}`lewis2020rag`，核心就是把检索器与生成器串成一条流水线，让检索到的上下文去约束生成器的输出。Gao 等人较新的一篇 RAG 综述 {cite}`gao2023retrieval` 把这个家族的变体都梳理了一遍 —— Naive RAG、带查询改写和重排的 Advanced RAG、Modular RAG —— 是一张很好的设计空间地图。撕掉表面那层漆，本书其实是一本“应用型 RAG”书：文本层（第二部分）和代码层（第三部分）是同一个模式的两种特化。

### 评估：BEIR 和它的朋友们

没有评估的检索就是迷信。BEIR {cite}`thakur2021beir` 是那套让零样本检索评估能在多领域具体做起来的基准集，它用的那套方法 —— 标注查询、nDCG@10、Recall@k —— 可以一对一搬到一个自建的代码知识库上。第 15 章会给一个代码层实例搭一个 mini-BEIR；要是不搭这套脚手架，就去比较 BM25 基线和 pgvector 后端的系统，最容易犯的错就是把“回答看起来不错”当成“回答是对的”。

### Vanilla RAG 的边界

本书口径下的“Vanilla RAG”，意思是：把文档切成大约段落大小的 chunk、给每个 chunk 算 embedding、按向量相似度取 top-k、拼成 prompt、调 LLM。这个基线在 demo 阶段的效果好到足以独占大众对“RAG 是什么”的全部想象，也有一份已经很出名的失败模式清单 —— 只要真实用户开始问真实问题，它们立刻就会浮出水面。下面五条值得点名：

1.  **chunk 边界问题。** 200 词一切，一个段落被劈成两半；解释 *"为什么"* API 返回 `nil` 的那句话在 chunk `k` 里，展示 *"返回了什么"* 的那句话在 chunk `k+1` 里，而按单 chunk 相似度打分的检索器只会返回其中一个。症状：答案看似合理，但丢了限定条件。缓解方案包括重叠 chunk、父文档检索和 late-chunking 等策略；没有任何一种能彻底解决，而且所有面向代码的知识库都必须按*语法*边界而非字符边界来切分（第 10 章）。

2.  **语义匹配 ≠ 语义相关。** 向量相似度找到的是*看起来像*查询的东西，而不是*回答*查询的东西。查询 "how do I rate-limit the ingest endpoint?" 会通过向量相似度召回仓库中最多谈论限流的五段话 —— 其中没有一段是专门关于 *ingest 端点* 的。修复方案几乎总是混合检索加上交叉编码器 reranker（见上面"重排"一节）；重排这一步，是很多"只加向量"栈跳过的那个诚实的步骤。

3.  **多跳 / 全局问题。** Vanilla RAG 召回的是一组扁平的 top-k chunk。像 *"这个代码库的三个主要主题是什么？"* 或 *"过去十个 commit 里 ingest pipeline 是怎么演变的？"* 这类问题，需要对结构进行推理，而 top-k chunk 不携带这种结构。这类问题的诚实回答是：*vanilla RAG 回答不了*。这正是 GraphRAG（下一节）要解决的缺口 {cite}`edge2024graphrag`。

4.  **索引过期问题。** 在 commit `a1b2c3d` 处构建的 embedding 索引，就定义而言是一份快照。在那份快照和用户查询之间，仓库已经动过了；函数被改了名、页面被重写了。除非流水线在每次变更时都重新计算 embedding（昂贵），或者检测并只重新计算受影响的文件（运维复杂度高），否则召回的 chunk 是一份已经不存在的文件的"前像"。第 14 章整章都在讲如何约束这个差距。

5.  **忠实性问题。** 即使检索完美，生成器仍然可能编造。尤其是代码 LLM，有文献记录表明它们会生成看似合理的 `file:line` 引用，但实际上没有对应到任何真实的文件或行 {cite}`chen2023faithfulness`。唯一持久有效的缓解措施是*机械式引用验证*：LLM 输出的每一个 `file:line` 都必须在构建的 HEAD commit 处能被解析到，否则答案会被门控拒绝（第 15 章）。

这五条都不是放弃 RAG 的理由 —— 而是让你别再把“vanilla RAG”当成 *“那个 RAG”* 的理由。文献把这个缓解层叫“Advanced RAG” {cite}`gao2023retrieval`；本书直接叫它 *“真正要干的那些活”*。

### GraphRAG 以及它的邻居们

GraphRAG 由 Microsoft Research 的 Edge 等人提出 {cite}`edge2024graphrag`，它针对的正是上面第三条 —— 全局问题 / 多跳问题。直觉不复杂，工程实现则不简单。它不再是召回一组扁平的 chunk 再指望 LLM 自己把它们重新“缝”起来，而是在建索引时就*预先算好*这种“缝合”：从语料里抽取实体和关系、建成一张图，然后在回答全局问题时，总结的是这张图，不是那些 chunk。

具体来说，论文里的 GraphRAG 分四个阶段：

| 阶段 | 输入 | 输出 | 谁在出钱 |
|:--|:--|:--|:--|
| **1. 实体抽取** | 原始 chunk | 带类型的实体 + 关系（由 LLM 抽取 prompt 完成） | 建索引期的 LLM 调用，O(chunks) |
| **2. 图构建** | 实体与关系 | 一张知识图谱（节点 = 实体，边 = 带来源信息的关系） | 便宜 |
| **3. 社区检测** | 整张图 | 通过 Leiden 等算法产生的层次化聚类（“社区”） | 便宜 |
| **4. 社区摘要** | 每一个社区 | 层次结构每一层上，由 LLM 生成的摘要 | 建索引期的 LLM 调用，O(communities) |

查询阶段 GraphRAG 有两种模式：**local（局部）** 搜索 —— 从查询里提到的实体出发，在图上行走，把它们的摘要召回来；**global（全局）** 搜索 —— 把查询同时打到*每一份*顶层社区摘要上，用 map-reduce 的方式合并答案。全局模式恰好是 vanilla RAG 字面意义上做不到的事：每一份社区摘要，都是在能完整看到该社区所有 chunk 的前提下生成的，因此 map 这一步才有机会，对一个全局提问给出一个全局正确的回答。

由此直接推出两条实操结论：

1.  **GraphRAG 不比 vanilla RAG 便宜。它走的是另一条成本曲线。** 建索引成本急剧上升 —— 典型值是比 vanilla RAG 多一到两个数量级的 LLM 调用 —— 换来的是查询期可以回答 vanilla RAG 根本回答不了的问题。如果你的查询全是 "what does `drainOnShutdown` do?" 这种，GraphRAG 就是白费力气。如果有不可忽视比例的查询是 "这个代码库的三个主要子系统是什么，它们之间怎么通信的？"，那么 GraphRAG 在头十几条查询上就能把建索引的成本赚回来。
2.  **抽取出来的图是产品，不是副产品。** 这张图是可以人工检查、人工修正、并可复用于 RAG 之外用途（可视化、影响分析、新人上手）的。采用了 GraphRAG 的团队，最终往往发现自己更看重那张图，而不是那些摘要。

一个值得关注的邻居是 **HippoRAG** {cite}`gutierrez2024hipporag`，它保留了 GraphRAG 的知识图谱结构，但把 Leiden + LLM 摘要这一步，换成了受海马体“记忆索引”模型启发的、基于个性化 PageRank 的检索。HippoRAG 报告称，在多跳问答上质量可对标 GraphRAG，而建索引成本显著更低。它在代码知识库这个特定场景上能否泛化，截至 2025 年仍是一个开放问题 —— 但这个方向（图结构 + 便宜的图算法检索，而不是昂贵的 LLM 预摘要）值得一直盯着。

本书不要求你在 GraphRAG 和 vanilla RAG 之间站队。第五部分（第 19 章）会用一张小型知识图谱做一件窄的事 —— 为代码做“引导式上下文装配”（guided context assembly） —— 在精神上更接近 GraphRAG-local，而不是 GraphRAG-global。设计问题永远只有一个：*哪一类问题对我而言最难，以及能让这一类问题变得可回答的、最便宜的结构是什么？*

## 怎么做

七个定义还告诉不了你 *先搭哪个检索器* 。一个合理的上手顺序，也是本书采用的顺序，是这样的：

0.  **先从朴素全文搜索开始** —— 在仓库上跑 `rg`，或在一组 markdown 笔记上跑 SQLite FTS5 —— 甚至还没写 chunker 之前就可以做 {cite}`fanyamin2026kb_pipeline`。如果这一步都不好用，下游什么也救不了你：embedding 不会让糟糕的文件组织变得可搜索。绝大多数个人知识库、以及相当一部分项目知识库，至今还停在这条线以下。
1.  **升级到 BM25**，时机是全文搜索开始跟不上了 —— 当你需要按词项稀缺度排序、需要字段加权、或需要短语匹配。BM25 几乎是免费的，而且它是一条真正的基线：*如果 BM25 基线都能赢你，那你还不算有检索系统，你只有一个带装饰的向量库。*
2.  **加稠密检索**，时机是你负担得起 embedding、并且至少有一类查询 BM25 明确搞不定。对代码知识库而言，这类查询就是"意译式意图"（第 10 章）。
3.  **用 RRF 融合词法和稠密** {cite}`cormack2009rrf`，前提是两个检索器各自独立跑起来了。融合让两个系统都变好、而且*几乎不会*让任何一个变差 —— 但前提是两边各自都是正常的。
4.  **加交叉编码器 reranker**，仅在融合 + 字段加权 + 新鲜度衰减都量化过、并且*精度仍然还有余量没用完*的时候 {cite}`nogueira2019passage` {cite}`reimers2019sbert`。Reranker 替换的是融合列表的 top-k 切片，不是融合列表本身；第一阶段 top-100 经过重排缩减到第二阶段 top-10 是标准形态。如果知识库在 top-3 的精度上已经够好了，就跳过这一步 —— 在那种条件下加交叉编码器只是在买延迟。
5.  **加生成器**，仅在检索和重排都已经量化过之后。检索好但生成差的答案是引用问题；检索差但说得流利的答案是幻觉问题。本书把后者视为更昂贵的故障模式，因此把生成器的调优推迟到第 13 章。
6.  **调任何东西之前先做评估** {cite}`thakur2021beir`。这是所有人都跳过的那一步。本书不会跳过。
7.  **只有当查询负载要求时，才考虑 GraphRAG** {cite}`edge2024graphrag`。如果超过大约 20% 的真实查询是全局框架的 —— *"主要组件有哪些"、"X 是怎么演变的"、"哪些模块依赖哪些"* —— 成本曲线就倾向于图。如果查询大多数是局部的 —— *"X 是从哪里被调用的"、"Y 返回什么"* —— 就不倾向。

作为本书底稿的那篇博客 {cite}`fanyamin2026deepwiki`，用的是同一个核心顺序，并以此反驳那种它称为“Demo 级做法”的路线：直接“塞数据然后喂给 LLM”，既没有排序基线，也没有评估脚手架。本章把博客里隐含处理的第 0 步、第 4 步、第 6 步和第 7 步，显式补了出来。

### 怎么选检索底座

在第 2 步和第 3 步之间的某个时刻，你就再也藏不进 *“向量库晚点再选”* 这句话后面了。底座 —— 真正帮你存索引、搜索引索的那个东西 —— 会实打实地约束住本章里提到的每一根操纵杆。字段加权、新鲜度衰减、结构化过滤、混合融合：每一项在不同底座上，要么就是一行配置的内建能力，要么就是一个从零做起的工程。截至 2026 年，现实的选择基本只有下面四种，以及它们各自配得上的负载 {cite}`fanyamin2026pgvector_rag` {cite}`fanyamin2026elasticsearch_rag`：

| 底座 | 适合的场景 | 何时值回票价 | 什么情况下直接跳过 |
|:--|:--|:--|:--|
| **朴素全文搜索**（`rg`、SQLite FTS5、PostgreSQL 的 `tsvector`） | 你是一个人在战斗；整个语料能装下一台机器；真正难的问题是 *“找到那份文件”*，而不是 *“给段落排序”*。 | 成本为零；延迟在亚秒级；完全不依赖任何模型。 | 当你需要“意译匹配”、或是在几十份文档间做有排序的 top-k 时，就该换了。 |
| **PostgreSQL 上的 pgvector** | 你本来就在用 PostgreSQL；向量数量在几百万以下；你希望向量能和业务表直接 `JOIN`。 | 没有新增任何运维面；ACID 天然具备；一条 `CREATE EXTENSION vector` 就开张。HNSW + 余弦距离在毫秒级别就能搞定绝大多数意译查询。 | 当你需要原生的 BM25、字段加权、函数评分 —— 虽然也可以用 `tsvector` 往上叠，但那时你写的其实就是 Elasticsearch 自带的那些功能。 |
| **Elasticsearch / OpenSearch** | 你在一次查询里同时需要 BM25、向量、结构化过滤、字段加权和新鲜度评分；你的用户用字面标识符搜索的频率，和用意译搜索的频率不相上下。 | 带 RRF 的原生混合检索、用 Function Score 做衰减、用 bool 查询做过滤、用 Kibana 检查数据质量。 | 你没有 JVM 运维能力；单节点撑不住你的流量；团队里没人有用它的经验。 |
| **专用向量数据库**（Pinecone、Milvus、Qdrant、Weaviate 等等） | 语料量达到千万级及以上；你需要多租户隔离、自动分片，或者托管化的 SLA。 | 规模与托管服务 SLA 已经超出一套 pgvector 或 ES 集群的能力范围。 | 当语料只有几百万规模、你很看重成本可见性、而且也根本用不到那些“规模旋钮”时，就别碰了。 |

本书的文本层示例放在 pgvector 里完全够用；代码层示例更大，但也仍然住在 pgvector + BM25 的混合方案里。两边都不需要 Elasticsearch，更不需要专用向量数据库。这不是巧合 —— 这恰恰就是一个软件项目知识库的*典型*规模。“默认先用最简单的”原则就是：**先上 pgvector；只有当字面标识符查询和意译查询混在一起、逼得你不得不升级时，才加 Elasticsearch；专用向量库则留给那道你大概率永远也不会撞上的规模悬崖** {cite}`fanyamin2026pgvector_rag`。

## 示例

一个玩具语料就够了。设想一个 Go 仓库里的四段代码：

```text
D1  func runSync(ctx context.Context) error { ... }   // internal/worker/pool.go:40
D2  defer func() { if r := recover(); r != nil { ... } }  // internal/worker/pool.go:55
D3  func drainOnShutdown() { ... }                     // internal/worker/pool.go:287
D4  // how to safely shut the worker pool down        // doc/runbook/shutdown.md:12
```

下面三条查询，以及每种检索器会怎么给它们打分：

| 查询 | BM25 的赢家 | 稠密的赢家 | RRF 的赢家 | GraphRAG 的赢家 |
|-------|-------------|--------------|------------|-----------------|
| *“谁调用了 `runSync`”* | D1，其次 D3（标识符匹配） | D1，其次 D3 | D1 —— 两边一致时代价最低 | 通过调用图上 `caller → runSync` 这条边找到 D1 |
| *“我们怎么等 worker 执行完”* | D4（关键字 “wait” / “workers” 命中），但漏掉了 D3 | D3（“drain on shutdown” 的意译） | D3 和 D4 都排在前面 | 从 `worker-pool` 社区出发沿图行走找到 D3 |
| *“这个 package 里关于 shutdown 的主要关注点有哪些”* | 四个里没有哪一个是明显更好的 | 同上 —— 稠密会在任何单一 chunk 上过度加权 | 同上 —— RRF 无法凭空造出一个全局视角 | 一份预先算好的 `shutdown` 社区摘要 |

前两行支持“混合检索”的论点：任何一个检索器单独上，都没办法同时答好这两条查询。第三行则是“GraphRAG”的论点：不论 BM25、稠密，还是它们的融合，都没办法从四段互不相连的 chunk 里给出全局答案。你可以逼 LLM 猜一个答案，但你逼不出任何一个上述检索器去*真正找到*它。第 12 章会走一遍代码层参考实现里真实的 RRF 代码，并度量它在真实查询上的效果；第 19 章会对一张“GraphRAG-local 风格”的代码图做同样的事。

有一种需要读者对比权衡的对立观点：**纯稠密检索 + 长上下文塞进去**，也就是很多 *“直接把整个仓库甩给 Gemini 2.5 或 Claude Opus 4”* 路线的形态。对规模小、流量也小的仓库，这样做完全可以胜任，而且有一个明显的优点：基础设施归零。它的缺点则是延迟、成本，以及 —— 这一点最关键 —— 它丢掉了结构化过滤：*“只要 `worker` 包里的函数”* 在 BM25 索引上是一行谓词，在一个纯上下文流水线里则是一场 prompt 工程噩梦 {cite}`fanyamin2026deepwiki`。而且原则上，它对上面第三行那种全局问题，也不会比 vanilla RAG 答得更好：一百万 token 的上下文，没有结构，依然只是一袋 chunk。

## 小结

四句话总结本章，也为全书后文立起框架。

*检索真正难的部分是排序；生成反倒是容易的那一半。* 先去调生成器、再去调排序器的团队，最后得到的是一台高速运转的胡说八道机器。本书默认这条教训已经被你吃过了 —— 每一个检索器都要先于它的生成器、每一次基准评估都要先于它要评估的那个检索器、每一个引用都要先于它所支撑的那个答案。

*Vanilla RAG 是基线，不是终点。* 它的五条边界 —— chunk 边界、相似 vs. 相关、多跳鸿沟、索引过期、忠实性 —— 都是工程问题，也都有工程解。本书接下来的每一章，都是这些工程解的展开版。

*GraphRAG 不是 vanilla RAG 的升级版；它是为另一类问题准备的另一条成本曲线。* 查询是全局框架下的，就用它；不是，就不用；不管用不用，都要记住那张图本身就是资产 —— 它活得比任何一个具体的检索策略都久。

*底座是负载决定的，不是时尚决定的。* 在 `rg`、pgvector、Elasticsearch 和专用向量数据库之间做选择，应该由你查询的形状和语料的规模决定，不应该由上个月谁上了 Hacker News 的热门决定。最常见的错误是 —— 跳过第一个选项，然后去为最后一个选项付钱。
