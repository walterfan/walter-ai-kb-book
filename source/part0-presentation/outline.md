# Speaker Outline —— 分钟级节奏表

```{admonition} 使用方式
:class: tip

这一份是讲者的 **口袋小抄**，不是完整稿。每一个 3-5 分钟的段落列出：

- **目标**：这几分钟要让听众 *记住* 哪一件事。
- **钩子**：用什么话 / 什么图 / 什么反问把听众拉住。
- **可跳**：时间紧时可以砍的部分（delta 值是节省的分钟数）。
- **别讲**：**一定**不要陷进去的细节。
- **深一层**（可选）：如果气氛好、时间够，多讲一句反直觉的话。

所有内容都指向 `index.md`（可读稿）里的对应节。开讲前请至少通读一次
`index.md`，再把这份 outline 打印出来放在讲台上。

**术语约定**：讲稿里直接用英文的概念 —— `Prose / Code / Dual Stack /
frontmatter / footer / tuple / retrieval / embedding / graph / RRF /
MCP / agent / commit-not-pages / L-git / L-entity / L-link`。
中文硬翻会丢细节，不如不翻。
```

## 总览（60 分钟）

| 段落 | 分钟 | 累计 | 节奏 |
|:--|:--:|:--:|:--|
| 开场 —— 周二下午的故事 | 3 | 3 | 故事、放慢 |
| Why —— 为什么需要软件 KB | 5 | 8 | 论证、不急 |
| What —— 六个 Part 一张图 | 5 | 13 | 画图、指框 |
| How —— 六个灵魂概念 | 22 | 35 | **保留 1 分钟缓冲** |
| Example —— 三段 demo | 20 | 55 | **必演**，失败切截图 |
| Conclusion —— 带走的三句话 | 2 | 57 | 快收尾 |
| Q&A | 3+ | 60 | 留给同事 |

**排演过两轮以上再上台**。第一轮光讲稿（不开 demo 也不放片），确认自己对
*流畅度* 有信心；第二轮完整跑一次 demo，**一定**用 live 代码跑过，记下
`sync` 步骤大约的 wall-clock（开分享的机器不同）。

## 0:00 – 0:03  开场（3 分钟）

- **目标**：让听众**代入**一个新同事的周二下午。
- **钩子**：第一张 slide 只有一句话 —— *"`runSync` 是在哪儿被调用的？"*
  —— 停 3 秒，再说 "这是我们每天都在重复的一个下午"。
- **可跳**：不可跳。这 3 分钟是全场的"钩子"。
- **别讲**：不要马上说 "这本书的解法是……"，留到后面。
- **深一层**：可以轻轻加一句 —— "新同事其实没问'怎么用'，她问的是'这段
  代码被谁用'。绝大多数文档工具只回答前者。" 这一句会让听众意识到
  今天讲的不是"写文档"，是别的东西。

## 0:03 – 0:08  Why —— 为什么需要软件 KB（5 分钟）

- **目标**：把当前三种应对办法（写文档 / grep + 问人 / 把 repo 塞给 LLM）
  的 *结构性* 问题说清楚。重点在"塞给 LLM"这个诱人但错误的选择。
- **钩子**：问全场 —— *"在座用过一次以上'把整个 repo 复制给 ChatGPT'的
  举手？"* —— 等 3 秒，气氛出来再继续。
- **核心句** *（一字不漏念出来）*：
  > 软件知识是**两种**不同的东西：*Prose*（人写得好、LLM 写不好、漂移快）
  > 和 *Code*（机器查得准、人记不住）。绝大多数"文档工具"只处理第一种。
- **深一层**：可以挑破一个常见误解 —— "context window 再大十倍也救不了
  这个下午：问题不是上下文装不下，是**没有可验证的来源**"。
- **可跳（−2 min）**：可以不念三种办法，直接跳到"thesis"那句。
- **别讲**：不要辩论 RAG vs fine-tune。本讲不讲"LLM 的上下文工程"。

## 0:08 – 0:13  What —— 六个 Part 一张图（5 分钟）

- **目标**：让听众**拥有一张地图**。之后任何时候他们脑子里都有
  "我现在在哪儿" 这个坐标。
- **钩子**：这一张 mermaid flowchart 是全场**唯一的架构总图**。
  指着它说 *"我接下来只讲主脊上的 6 个灵魂概念，别的部分指给你们看，
  不展开。"*
- **操作**：在投影上**停留 30 秒** —— 不讲话，让图自己进脑子。
- **可选 research anchor（+2 min，可从缓冲里拿）**：如果现场有人担心
  这是个人方法论，就用三句带过：
  - *Zhu et al.* 说明 LLM 更擅长 reasoning than extraction；
  - *RepoAgent* 说明 repo 文档是"结构分析 → 生成 → 更新"的 pipeline；
  - *CGM* 说明图会进入 repo-level 理解，而不只是待在 retriever 旁边。

  **不要展开论文细节。**
- **深一层**：可以顺手点一句 —— "很多团队的 KB 在 Part IV 那里死掉：
  能建不能维护。今天的主脊有一半内容是讲 Part IV 的。"
- **可跳（−1 min）**：可以只念 Part II、III、V 的 one-liner。
- **别讲**：**别**开始讲 Diátaxis、BM25、HNSW 这些名词。留到对应段落。

## 0:13 – 0:35  How —— 六个灵魂概念（22 分钟）

每个概念约 3.5 分钟。**保留 1 分钟总缓冲**（被追问时可吸收）。

### 0:13 – 0:17  概念 1 —— frontmatter + footer（4 min）

- **目标**：一条铁律 —— **AI 写的页面永远 `pending`**。
- **操作**：投影上只放 footer 的 YAML 片段，**手指着 `review_status: pending`
  那行**。
- **深一层**：别小看 `pending` 这四个字母 —— 它是**检索排序、publish gate、
  agent 引用决策** 共用的最小可验证单位。没有它，KB 和 "一个拼写更好的
  markdown 文件夹" 没区别。
- **可跳（−2 min）**：可以不念 5 个字段全部，只讲 `updated_by` 和
  `review_status`。
- **别讲**：不讲 frontmatter 的完整 schema，不讲 Git 审计日志。

### 0:17 – 0:21  概念 2 —— Code 不是 Prose（4 min）

- **目标**：让听众**认同** Dual Stack（vector + graph）是必要的。
- **钩子**：继续用开场那个 `runSync` 的问题 —— *"vector retrieval 能告诉你
  '谁调用它' 吗？"*
- **核心**：三条主张（结构、精确匹配、关系）+ 一张 Dual Stack flowchart。
- **深一层**：三条主张都不是性能问题，是**语义类型错误** —— 把 "关系"
  当成 "相似度" 看。一旦同意这一点，vector + graph 的组合就不是"为了准"，
  而是"为了讲对"。
- **可跳（−2 min）**：三条主张只念**第 3 条**（关系），它最反直觉。
- **别讲**：不讲 tree-sitter / sqlite-vec / Memgraph 的细节。这些是选型
  题，不是主张。

### 0:21 – 0:25  概念 3 —— L0–L4 tuple（4 min）

- **目标**：让听众看到**单轴不够**。
- **操作**：并排放两张小表：单轴 5 行 + tuple 4 行。用颜色把"同是 L1，
  但一个 `human,approved,4`、一个 `ai,pending,0`" **高亮** —— 一眼就能看出差别。
- **深一层**：最反直觉的一行 —— "LLM 草稿 + 人审过" 的权重 (0.8) **高于**
  "人写 ADR + LLM 重写没审" 的权重 (0.3)。**权威来自'谁签了字'，
  不是'谁写的第一稿'**。这句话常常现场引起点头。
- **可跳（−2 min）**：可以不念 tuple 的公式，只念那张 retrieval 权重表。
- **别讲**：不讲 retrieval 权重的确切计算公式（第 18 章的 `L_w * R_w * S_w`）。

### 0:25 – 0:28  概念 4 —— Hybrid Retrieval + RRF（3 min）

- **目标**：一行公式 —— $\text{rrf}(d) = \sum_i \frac{1}{k + \text{rank}_i(d)}$。
- **核心句**：*"不同 retriever 的分数不在同一个量纲上。把它们加权相加
  是纯迷信。RRF 只看 rank。"*
- **深一层**：可以丢一个具体数字 —— "同一个文档在 retriever A 拿 0.82、在
  B 拿 14.7。加权平均是把两个不同单位的数字强行相加，没有物理意义。
  RRF 把问题降到'排名'这个**跨 retriever 不变量**上。"
- **可跳（−1 min）**：可以不念三层漏斗，只念公式 + 一句"为什么分数融合
  是迷信"。
- **别讲**：不讲 cross-encoder rerank、不讲 ColBERT。留给有兴趣的人。

### 0:28 – 0:32  概念 5 —— 三级更新策略（4 min）

- **目标**：让听众拿到 "Rule first, LLM second" 这句话。
- **核心**：一张 3 行表（L1 脚本 / L2 受限 LLM / L3 人类）+ 一条铁律
  （AI → `pending`）。
- **深一层**：顺序反过来的代价 —— "把能脚本的事交给 LLM，成本翻十倍；把
  能 LLM 的事叫人，评审会先弃权"。这不是节省美金，是**保护评审者的注意力**。
- **可跳（−2 min）**：如果时间紧，把第 6 个概念（预算）合并到这个段落里
  讲 —— 它们本来就是一件事。
- **别讲**：不讲 dispatcher 的具体算法。

### 0:32 – 0:35  概念 6 —— commit-not-pages 预算（3 min）

- **目标**：这是全场**最想让人记住的一句工程纪律**。
- **核心句** *（慢一点，重一点）*：
  > 一个 KB 的 LLM 成本，应该是 *提交次数* 的可预测函数，而不是
  > *页面数* 的函数。
- **深一层**：它的反面是一条漂亮的死路 —— "KB 越有用越大 → 每次 commit
  越贵 → 预算爆掉 → 停止维护"。commit-not-pages 就是把这条曲线
  **从 O(KB size) 拽回 O(change rate)**。
- **数字**：*"19 candidates、每 repo 每周几美分。naive baseline 贵十倍
  以上。"* 不用细讲公式，数字就够。
- **可跳**：不可跳 —— 这是本场的收尾句式。
- **别讲**：不讲 `text-embedding-3-small` 的具体单价。

### 0:35 – 0:35（+1 min 缓冲）

如果时间超了，从缓冲里扣。如果时间还早，扩展概念 2 的第 3 条
（"Graph-free design" 那条反 pattern 特别好讲）。

## 0:35 – 0:55  Example —— 三段 demo（20 分钟）

**务必在开讲前 15 分钟把 demo 跑一遍**——环境热身（embedding API 预热、
终端字号调大、iTerm 拆屏）。

### 0:35 – 0:43  Demo 1 —— 增量同步：36× / 180× / 9×（8 min）

- **三个 × 是什么**：同一次实验里，**全量** `code-kg sync`（约 ~3 min 墙钟）
  相对 **一行 diff 后的增量** `code-kg sync --incremental` 的提速比（博客 /
  书里那张表的形状）。不是三个独立 demo，而是**三条管线/配置**上各算一遍
  比值：
  - **36×** —— **仅关键词**路径：全量 ~3 min → 增量 ~5 s 量级（没端到端重跑
    embedding 时的「地板」）。
  - **180×** —— **向量 / embedding 端到端**：全量 ~3 min → 增量不到 1 s；多数
    实体向量不必重算，所以数字最大（下面「深一层」要讲清原因）。
  - **9×** —— **图重建**：全量 ~3 min → 增量 ~20 s；子图仍要实质更新，所以
    比向量小得多，但仍远快于全量。
  具体秒数随硬件和仓库会变，现场讲 **数量级关系** 即可。
- **目标**：把博客里那个表 **重现一次** —— 不是为了证明数字漂亮，
  而是为了让 "stable entity ID 让增量同步敢于 delete-then-insert"
  这件事有**手感**。
- **演示顺序**：
  1.  先 `code-kg sync`（全量，~3 min）—— **开讲之前先跑好**，现场直接展示输出。
  2.  现场改一行代码 + commit。
  3.  现场 `code-kg sync --incremental`，**指着输出里那三行时间**。
- **深一层**：强调 180× 不是"向量很快" —— 是 **stable ID + L-git /
  L-entity / L-link 三层过滤** 把 99 % 的工作挡在了增量处理之外。
- **失败 fallback**：截图（`docs/demo-screenshots/incremental-sync.png`）。
- **别讲**：不讲 Merkle diff 的原理。不讲 `SyncJob` 状态机。

### 0:43 – 0:51  Demo 2 —— agent 通过 MCP 调 KB（8 min）

- **目标**：让听众**看到** agent 一次 round-trip 里具体发了哪三个 MCP 调用。
- **演示顺序**：
  1.  在 IDE（Cursor 或 Claude Code）里开一个调试面板（MCP call log）。
  2.  输入 `/ask "ingest pipeline 是怎么处理 CSV 的?"`。
  3.  指着调用日志里的 `kb.search` → `kb.read`，让听众看到**参数和返回**。
  4.  追问 "具体是哪个文件？"，触发 `kb.cite`，指那个 `file:line` 锚点。
- **深一层**：点一下"真正革命性的一件事不是 agent 会调 API，是 agent
  开始读 footer —— 它第一次拿到了'要不要相信这一页'的**机器可读信号**"。
- **失败 fallback**：`index.md` 里那段 "08:15 / 08:17" 的文字脚本直接投影
  （听众能读懂，够用）。
- **别讲**：不讲 MCP 协议的 JSON-RPC 细节。不讲工具注册的 manifest。

### 0:51 – 0:55  Demo 3 —— publish gates（4 min）

- **目标**：让 KB 的 "工程化" 这件事**落地成一个 `make` target**。
- **演示**：
  1.  现场 `make book-check`。
  2.  指输出里的 `H*` 和 `S*` 标识 —— **"hard 挡 publish、soft 只告警"**。
  3.  现场把一个 `{cite}` key 拼错，再跑一次 —— 看到 H4 失败。
- **深一层**："一个 KB 成熟" 的定义：**不是没错，而是错会被抓住**。
  对比 wiki 烂掉的典型路径 —— 没人知道它烂了。publish gate 的价值是
  **把腐烂变成一个机器可见的事件**。
- **失败 fallback**：示意截图。
- **别讲**：不讲每一条 gate 的具体实现脚本。

## 0:55 – 0:57  Conclusion —— 三句话（2 min）

- **目标**：**慢**。这 2 分钟不要赶。
- **操作**：一张 slide，三句话，念一条停 3 秒：
  1.  Code 不是 Prose。别 dump 整个 repo。
  2.  AI 写的页面**永远 `pending`**。
  3.  按 commit 预算，不按页面。
- **深一层（可选）**：可以轻轻说一句 —— "这三句话背后是三种工程纪律：
  对结构的尊重、对审阅的敬畏、对成本的诚实。"
- **最后一句**：*"如果你只有 20 分钟阅读预算……"* —— 把三条 "reading path"
  念出来，留三个**可打开书就用**的入口。

## 0:57 – 1:00+  Q&A（3 分钟+）

- **可预期问题**（提前准备答案）：
  - *"用 Copilot 已经够了，为什么还要造 KB？"* —— Copilot 没 `file:line`
    citation，agent 复述是错的也无法追责。KB 是 agent 的
    **可验证 ground truth**。
  - *"这套 tree-sitter + sqlite-vec + Memgraph 在我们栈上能跑吗？"* ——
    这是选型题，第 15 章有 upgrade matrix；今天不展开。
  - *"L1 比例低于 20% 怎么办？"* —— 第 22 章明说：「规则没覆盖常见场景，
    或 KB 不自然地偏 L2」。先看前者。
  - *"内部代码能丢给外部 LLM 吗？"* —— 第 22 章的 "bounded disclosure" ——
    敏感路径打 tag，走自部署模型；第 16 章的 L2 上限 5 k token 本身
    就是隐私护栏。
- **回答原则**：
  - **不硬答**。一个诚实的 "这是好问题，会后补" 比十个漂亮的 hallucination
    有价值。今天整本书讲的就是这个。
  - **不会答的问题**：记下来，说 "会后写在分享频道里"。
